# RMD-1802 — Durable worker/control/enqueue race review (2026-10-10)

Status: implementation on `master`; independent review and final closeout **remain open**.

- Exact master `79743096567e640d7d18220a169370c7f62e12c1` passed all eight required push workflows: normal CI `38117307644`, Android smoke `38117307612`, FGS timeout `38117307652`, Supply chain `38117307610`, deterministic fixture E2E `38117307621`, Android cold start `38117307591`, Android real-network E2E `38117307573`, and CI evidence `38117307557`. This SHA already included atomic queue-claim and stale-startup-recovery compare-and-swap.
- Independent review found that `FfiDownloadControlService::transition_inner` and `retry_inner` were still saving stale queue snapshots unconditionally; pause/cancel/retry could overwrite a concurrent worker's newer state. Commit `b6d0f44c1960777e5ba736ab44ce7c7441ea5d63` uses `LibraryStore::replace_download_snapshot_if_unchanged` on those control paths, with deterministic stale-pause, stale-completion, stale-retry and valid-control tests. Rustfmt correction: `3245160f46991e992d4c91eb91fb82bd8fd1c13b`.
- Independent review then found that `FfiDownloadControlService::enqueue_inner` checked for duplicate job IDs before writing the executable work plan and queue state in separate transactions. Two concurrent calls could observe absence then clobber each other's queue state or stored executable plan. Commit `d43f39714fa708336dcda1f10afffe5f308189b6` introduced `DurableDownloadWorkStore::enqueue_if_absent` as one SQLite transaction for queue/plan/presentation and `LibraryStore::insert_download_snapshot_if_absent` for queue-only work. Deterministic regressions assert duplicate enqueue cannot replace an existing plan/presentation or an already-active queue job.
- The first exact-head CI on `d43f39714fa708336dcda1f10afffe5f308189b6` failed only `cargo fmt --check` in Rust gate `38119479475`; no passing full matrix is claimed for that SHA. The next commit applies formatting and must be separately exact-head qualified.

Do not mark RMD-1802, RMD-1803, RMD-1804, RMD-1805 or global rules checked until independent review is complete, the final frozen SHA passes the full required CI matrix, and canonical TODO evidence reconciliation is complete. Live YouTube/service-policy/legal approval remains a separate external gate.

- Further production review found a claim-to-transfer startup race in `core/src/worker.rs::execute_one`: after an atomic queue claim, a concurrent pause/cancel could be overwritten by an unconditional `Downloading` save. Commit `465809d4dbd80e9c141f60ff6fbbdebf1eb2e7db` changes that transition to a compare-and-swap against the previously claimed snapshot; stale startup now aborts before transfer. The canceled-state report path preserves the already-durable cancellation instead of overwriting it. `pause_after_claim_prevents_stale_worker_from_starting_transfer` checks queue, staging, and Library state without relying on network or emulator. Exact-head qualification remains required after this formatting follow-up.

- RMD-507/RMD-G06 review exposed a separate progress metric defect in `DownloadWorker::execute_one`: `progress_epoch_ms` was incremented by a fabricated 1,000 ms per asset regardless of actual transfer duration, so reported bytes/second and ETA could be inaccurate. The follow-up uses `std::time::Instant` elapsed time anchored to the injected epoch and updates known/unknown-length HTTP fixture tests to use observed transfer delay rather than asserting a synthetic exact rate. Full exact-head CI evidence is required before closing this finding.

- Subsequent final-settlement review found that Verifying and Completed transitions in `DownloadWorker::execute_one` and `LibraryStore::promote_completed` were unconditional writes, so a user cancellation could be overwritten after the network transfer ended. Commits `27f82b4f6e26c27fadeb95fda9d5b148fb0e27e7` and `ca91e6d887200daeac9fc603c42ea485e74371c3` provide CAS-backed verification and transactionally guarded completion plus deterministic cancellation/prevented-promotion coverage. See `docs/RMD_1802_ATOMIC_COMPLETION_REVIEW_2026-10-11.md`. Leave global/final closeout open until final exact-head qualification.
